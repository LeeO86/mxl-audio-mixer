# mxl-audio-mixer 1.0.0 — release notes

The first release (§19): milestones 0–6. A broadcast audio engine on MXL with
NMOS IS-04/IS-05: the matrix and DSP, the console, the control room with MXL and
WebRTC monitoring and talkback, VCAs, N-1 and group operations, the widgets
`strip`, `fader-bank`, `loudness`, `monitor`, `talkback`, `vca`, and tally with
audio-follows-video. MIT licence.

The scheduling run on the tag (`14e9487`) is recorded below. A node that gives
the DSP thread a whole core is still the check of the 0-misses rule.

`MIXER_CONFIG_FILE`, then the defaults; an invalid value exits with 78.

## Volumes

- `MIXER_STATE_DIR` (`/config`): writable, persistent (the show file, the
  connections, the show history, the built-in MediaMTX's configuration).
- The MXL root at `MXL_DOMAIN_SCAN_PATH` (`/Volumes/mxl`, hostPath): the input
  domains and the mixer's own output domain (`MXL_OUTPUT_DOMAIN_DIR`).

## Exit codes

| Exit code | Meaning |
| --- | --- |
| 0 | stopped by Ctrl-C |
| 75 | a port cannot be bound (TSL ports with `TSL_ENABLE=true`, the built-in MediaMTX's ports without `PREVIEW_PUBLISH_URL`), or the DSP thread cannot start |
| 78 | invalid configuration, libmxl missing, output domain id clash |
| 143 | SIGTERM: media stopped, MXL released, node deregistered, own domain removed with `MXL_CLEANUP_ON_EXIT=true`, within `SHUTDOWN_TIMEOUT_S` |

## What the platform must set

- `NMOS_HOST_ADDRESS`: the pod IP. `HOST_ID` and `NMOS_SEED` stable per instance
  (every NMOS id and MXL flow id derives from the seed).
- `NMOS_REGISTRY_ADDRESS` and `NMOS_REGISTRY_PORT` (the Query API defaults to the
  next port).
- `MXL_DOMAIN_SCAN_PATH` with the MXL root as a hostPath, and a writable
  `/config` volume.
- On the nodes: the kernel TAI offset (CLOCK_TAI = UTC + 37 s). `/readyz`
  does not wait for it (corrected 2026-10-16: the pod goes Ready anyway);
  watch `timing_trusted` in the `/readyz` details and the metric, and the
  "timing untrusted" error in the log.
- Guaranteed QoS with whole CPUs; `MIXER_RT_PRIORITY` (≤ 49) with the `SYS_NICE`
  capability, if wanted. The DSP thread (on the last of the pod's CPUs) needs
  that CPU's **whole physical core**: with SMT, the static CPU manager with
  `full-pcpus-only` (or SMT off), so no other workload runs on its sibling. The
  mixer keeps its own other threads off that core when it has CPUs on another
  one; `GET /api/v1/status` (`dsp.scheduling`) says whether the core is shared,
  and the mixer warns when the sibling is outside its CPUs. Measured: a busy
  sibling makes the DSP thread's blocks 3–4 times slower.
- Monitoring and talkback in browsers through the platform's MediaMTX:
  `PREVIEW_PUBLISH_URL`, `PREVIEW_PATH_PREFIX` (`<production>/<instance>`),
  `PREVIEW_WHEP_URL`, `MEDIAMTX_API_URL`. Without them the mixer runs its own
  MediaMTX and needs the ICE UDP port (8199) reachable on the node (hostPort).
  Browser talkback needs the UI on HTTPS. Its MediaMTX takes publishing from the
  network only on `<prefix>/talkback-<client>` paths.
- `WIDGET_FRAME_ANCESTORS` with the production designer's origin.
- `TSL_ENABLE=true` with the tally calculator's TSL UMD 5.0 target ports, for
  audio-follows-video.

`deploy/k8s/deployment.yaml` is an example.

2 ms block (0.854 to 0.358–0.367, the 0.34 expected). The DSP thread used 36 %
of its CPU and the meter thread 16 % of another (`perf`: no libm, no kernel
time left on the DSP thread). The deadline misses come from the shared core:
99 % of them (3321 of 3331 and 12 207 of 12 269 in per-second samples) fell in
the seconds the DSP CPU's sibling was busy with the other tenant; with the
sibling idle there were 10 and 62 in 814 and 1598 s. The CPU's clock stayed at
3.3 GHz. The block-clock runs (no DSP work) vary with the host's load over the
day. A verdict on the misses needs a node that gives the DSP thread its whole
core (above).

Missing input samples were 960 and 1824 on `208689e`, and 51 168 here (533
failed block reads, 51 168 / 96, about 1.07 s of audio in 60 min). The input
read runs on the DSP thread. Keeping the mixer's other threads off that core
does not move it, and the tone writers are other processes. The counter is the
same one: every failed read after the input has started, 96 samples a block.
`input_late_samples_total` (the source had not written the index yet) already
existed, and this load line did not print it, so the 51 168 are not split by
cause. Fewer deadline misses together with more missing samples does not fit
the reader falling out of the ring, which would have risen with the misses.
The next build prints late source, ring overrun and the remainder on the load
line (`input_overrun_samples_total` is the ring having already overwritten the
index).
