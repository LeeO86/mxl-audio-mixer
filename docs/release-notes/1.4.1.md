# mxl-audio-mixer 1.4.1 — release notes

Fixes to how inputs are read, from the 1.4.0 deployment on test-all. Released
2026-10-22. The image digest is filled in after the tag build.

## For the platform

- **`MIXER_READ_OFFSET` can go back to the default 2.** The gateway inputs that
  still lost a block every 30–50 s at 2 ms on 1.4.0 (rare packets several ms late)
  now raise their own delay at the first such block and keep it while the outlier
  recurs.
- **No setting, metric, API, port or show-file change.** `MIXER_INPUT_DELAY_HOLD_S`
  keeps its meaning; it also sets how long a late block holds the delay up (one
  hold time; ten while the same outlier recurs). `input_effective_delay_ms` now
  shows those rises.
- **Rollback to 1.4.0 is clean:** the same `mix.json`, inputs and connections.
- **inotify:** every distinct flow the mixer reads takes one MXL instance, that is
  one inotify instance (and a watcher thread); inputs reading the same flow share
  it. `fs.inotify.max_user_instances` (often 128 per uid, shared with every MXL
  process running as that uid, e.g. 1000) must leave room for them. An instance
  that cannot be created is logged at ERROR, naming the limit, and the input does
  not open (a waiting input tries again every 100 ms).
- After a start, deadline misses should be 0 (they were in the hundreds in the
  first minutes on test-all, partly from IRQs, partly from the mixer's read wait,
  fixed here).

## Changes (#44)

- **A late block raises the delay at once.** A block whose arrival lag is above
  the read offset plus the input's delay (the head moving) raises that input's
  automatic delay at once to the lag plus 1 ms, within
  `MIXER_INPUT_DELAY_MAX_MS`, also before the first second and regardless of the
  hold. Its need is a floor for one hold time; when an outlier of about the same
  size (within 1 ms and a block) comes again within ten hold times it recurs, and
  its floor lasts ten hold times, renewed by each recurrence. A one-off late block
  costs its latency for about two hold times (1 min); other sizes renew nothing,
  so the delay does not ratchet up. The DSP thread only reports lags.
- **One read wait per block.** A read waits up to a quarter block for samples
  that are almost there; each late input waited its own, so four or more late
  inputs (at the start, before their delays were set, or stalled) took longer than
  the block and every block missed its deadline. The wait is now one quarter block
  per block for all inputs.
- **A writer catching up is no lag.** After a stall or a re-open the lag counts
  only once the writer has caught up (back at its lag from before, or a head that
  kept real time for 0.5 s). Before, a resumed writer's catch-up set the delay to
  the maximum, 150 ms (also in 1.4.0). Lags beyond the read offset plus the
  maximum delay move no delay at all; they stay in the displayed lag (a writer
  always that late reads the edge of the measured range there; `lag_ms` is
  exact). A catch-up slower than about 1.125 times real time still counts.
- **A re-created flow gets a fresh reader.** libmxl caches one reader per flow per
  instance; an input re-opened on a flow deleted and re-created within about one
  tick (a writer restarted at once) could get the old reader back, mapped on the
  deleted files, and stayed stalled. MXL instances are now per flow generation
  (flow id and data-file inode), shared by the inputs reading it.
- `tests/integration/inputs.sh`: a rare 6 ms outlier (nothing lost after the
  first), five stopped writers (no deadline misses; skipped when the machine
  misses more than 50 in 3 s anyway; delays unchanged after they resume), two
  inputs on one flow restarted at once three times (both run, nothing deleted
  mapped).
