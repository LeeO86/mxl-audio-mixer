# mxl-audio-mixer 1.5.1 — release notes (draft)

One fix with a **behaviour change for the platform**: the mixer's outputs keep the
MXL timestamps of the input samples they carry. Before, every output was written
at the mixer's block clock ("now"), so audio that went through the mixer came out
later on the timeline than the video it belonged to. Not released yet.

## Upgrade and rollback — read first

- **Behaviour change: readers of mixer outputs may need a larger read offset.**
  A sample read from an input at MXL index i now leaves on every output (bus,
  direct out, monitor, published and virtual output) at index i. The mixer still
  writes it at the same moment as before, so against the output's own timestamps it
  writes "late", by the output's **write delay**. A reader with a read offset
  below the write delay gets late (too early) reads. Check every reader of a mixer
  output before the upgrade (below, "What the platform must set").
- No setting, port, show-file or mix change. A 1.5.0 `mix.json` loads unchanged.
- **Rollback to 1.5.0 is clean** (the mix loads); the outputs go back to the block
  clock (re-stamped by the read offset plus the input's extra delay), and the read
  offsets set for 1.5.1 still work (larger than 1.5.0 needs).

## What was wrong

Measured on the test platform with mxl-avsync: an AV-sync signal through the video
mixer (video keeps its MXL index) and through the audio mixer as an input routed
straight to a virtual output (C7) came out with the audio re-stamped by
`audio_index_shift` 39.25 ms (37.0–41.2), so the AV offset downstream was +39 ms.

Cause: the DSP thread reads each input at
`(n+1)·B − (MIXER_READ_OFFSET + the input's extra delay)` and wrote the output block
ending at `(n+1)·B`, the block clock (1.5.0 `src/engine/dsp.rs:564-565` read,
`:684` `commit(o, start + b, oc)`). The shift was therefore the read offset (2 ms) plus the input's
automatic extra delay, which follows how the source commits: a writer that commits
a 25 fps video frame of audio (40 ms) at once gets about 37–39 ms of extra delay.
That is also why the shift moved when the generator changed its write lead.

## What changes for the platform

- **Outputs keep the input timestamps.** Block n of an output ends at index
  `(n+1)·B − (MIXER_READ_OFFSET + d + L)`:
  - d is the largest extra delay among the inputs that reach that output (found from
    the plan: sends at gain 0 count, so a mute does not move the time; keys do not);
  - L is the output path's look-ahead (limiter `lookahead_ms`, the leveler's 1 ms
    safety limiter). It is compensated, so a limiter costs no sync. Gain, EQ, pan,
    filters and the other nodes have no algorithmic latency. An explicit delay node
    is the operator's choice and stays a delay.
  - An output that mixes inputs with different extra delays takes the largest. The
    inputs are still each read at their own delay (unchanged), so in such a mix they
    stay that far apart, as in 1.5.0.
  - Oscillators and talkback have no input time; they take the output's time.
- **Write delay**, new per output: `write_delay_ms` in `GET /api/v1/status`
  (`outputs[]`) and `GET /api/v1/virtual-outputs`, and the metric
  `mxl_audio_mixer_output_write_delay_ms{output}`. It is
  `MIXER_READ_OFFSET + d + L + commit + one block`: how far the output's head index
  can trail TAI now (one commit at a time, after the block's processing). It
  changes at run time with the inputs' automatic delays, so it is not an NMOS tag.
- **Changed metric meaning:** `output_commit_lag_ms` (TAI time of a commit minus the
  time of its last sample) now includes the offset `MIXER_READ_OFFSET + d + L`: it is
  the measured write delay without the commit and block margin (e.g. 43.0 ms for an
  input with 41 ms of extra delay; it was about 0.03 ms). Dashboards or alerts on
  it need new thresholds.
- **When d or L changes** (an input's automatic delay changes, an input with
  another delay is routed into the output, a look-ahead node is added or removed),
  the output's index jumps: the output fades out with the input whose delay changes
  (10 ms) and fades in after the jump; indices already written are not written
  again, a gap is written as silence.
- **Listening latency is unchanged** (monitors, in-ears, the browser preview, the
  remote link): the samples are written at the same moment, only their index
  changed. A control-room monitor published as an MXL flow follows the same rule as
  every output.

## What the platform must set

A reader of a mixer output needs a read offset of **at least the output's
`write_delay_ms`**, plus its own margin. With local inputs and the defaults
(2 ms read offset, 96-sample blocks and commits) that is about 6–9 ms; an input with
37 ms of automatic delay makes it about 43 ms.

- **mxl-st2110-gateway** (egress of a mixer output): per receiver `read_offset_ns`
  (or `read_offset_grains`), or `MXLGW_MXL_DEFAULT_READ_OFFSET_NS` /
  `MXL_READ_OFFSET_MS`. Egress reads a grain's video and audio with one offset, so
  for an AV pair the offset must cover the audio's write delay.
- **Video mixer, multiviewer, or any reader that aligns audio with video:** read the
  mixer's audio at least the write delay behind TAI now. The video path needs no
  extra delay: the audio now carries the video's timestamps.
- **Another mixer reading this one (remote link, chained mixers):** nothing to set;
  its automatic delay covers the write delay (`MIXER_INPUT_DELAY_MAX_MS` must be
  above it, default 150 ms).
- `MIXER_READ_OFFSET` stays 2.

## Measured

Lab, release build, test writer `mxl-mixer-tone --ramp` (each sample tells its
index) into input 1, straight to a virtual output and through a stereo bus at
−6 dB, read with `mxl-mixer-probe --ramp`, 10 s each (about 475 000 samples,
1.000 at the median):

| writer | 1.5.0 extra delay | 1.5.0 shift | 1.5.1 shift | 1.5.1 write delay |
| --- | --- | --- | --- | --- |
| 1920-sample batches (25 fps frame), on time | 39.1 ms | +41.1 ms | 0 | 47.0 ms |
| 1920-sample batches, 25 ms early | 37.0 ms | +39.0 ms | 0 | 43.0 ms |
| 96-sample blocks, on time | 3.0 ms | +5.0 ms | 0 | 9.0 ms |
| 96-sample blocks, 25 ms early | 0 | +2.0 ms | 0 | 6.0 ms |

With 47.0 ms of write delay a reader at 40 ms behind read clean (the probe waits up
to 5 ms), at 30 ms every read was too early. `tests/integration/vouts.sh` checks
shift 0 straight through, through a bus at −6 dB and through a 1.5 ms look-ahead
limiter, with an input 30 ms late (write delay 37.0 and 38.5 ms).

Not measured yet: the platform's mxl-avsync chain on 1.5.1, a mirrored output, the
remote link between two nodes.
